### - [x] FR-001: User Authentication and Session Management

- Module: Core - Authentication
- Type: Security
- Priority: Critical
- Status: Proposed
- Designed: 2026-08-06 by Senior Software Lead Designer (see `TODO.md` §1–§9)
- Requested By: Senior Software Solution Consultant
- Date: 2026-08-06
- Source Reference: Project.txt - System Architecture, Core Functional Requirements (Authentication)
- Target Roles: All roles

#### Business Objective

All users access one shared application, so the platform must positively identify every user before granting any access. Secure authentication is the foundation of the entire HRIS and protects all HR, attendance, and personal data.

#### User Story

As a user, I want to log in securely with my credentials and log out explicitly, so that only authorized individuals can enter the platform and my session ends when I finish working.

#### Requested Capability

The system shall support secure sign-in and sign-out for all users, identify the authenticated user's identity and assigned roles, and prevent unauthenticated individuals from reaching any protected area of the application.

#### Functional Expectations

- A user can sign in with valid credentials.
- A user can sign out, which immediately terminates their access.
- The system recognizes the authenticated user's identity and assigned roles after sign-in.
- Unauthenticated users attempting to reach protected pages are redirected to sign-in.
- Sessions expire after a defined period of inactivity and the user must sign in again.
- A user account is temporarily locked after a defined number of consecutive failed sign-in attempts, and unlocks automatically after a defined period.
- A user can view their active sessions and end sessions on other devices, while keeping their current session.

#### Acceptance Criteria

- Only users with valid credentials can access the application.
- Failed sign-in attempts do not reveal whether the username or password was incorrect.
- Signing out immediately prevents further access to protected content.
- Direct navigation to any protected page while unauthenticated is blocked and redirected to sign-in.
- After a defined period of inactivity, the session expires and requires a new sign-in.
- The authenticated user's identity and roles are available for authorization checks across the application.
- After the configured number of consecutive failed sign-in attempts, the account is locked and further attempts are rejected with a clear message.
- A locked account automatically unlocks after the configured lockout period.
- A user can view a list of their active sessions and end a session on another device; ending it prevents further access from that device.

#### Dependencies

- FR-002 (Role-Based Access Control and Permission Matrix Management)

#### Assumptions

- User accounts are provisioned by administrators; there is no public self-registration.
- Standard corporate password security expectations apply (strength and storage handled per security best practices, not specified here).
- Failed-attempt lockout thresholds and lockout durations are configurable platform settings (FR-032).

#### Risks / Open Questions

- Is multi-factor authentication required for any roles?
- What is the required session timeout duration?
- Should session lockout thresholds differ by role (e.g., stricter for administrators)?

#### Notes for Senior Software Lead Designer

Design an authentication boundary that is shared by the entire application and feeds identity plus roles into all downstream authorization checks. Keep session policy configurable.

### - [x] FR-002: Role-Based Access Control and Permission Matrix Management

- Module: Core - Authorization / RBAC
- Type: Security
- Priority: Critical
- Status: Proposed
- Designed: 2026-08-06 by Senior Software Lead Designer (see `TODO.md` §1–§9)
- Requested By: Senior Software Solution Consultant
- Date: 2026-08-06
- Source Reference: Project.txt - System Architecture, Core Functional Requirements (Authorization, RBAC), Example Roles
- Target Roles: Super Administrator, HR Administrator

#### Business Objective

The platform is shared by all users, so a single trusted permission model must decide what each user can see and do. Without a managed role and permission matrix, the system cannot enforce role boundaries or expand safely to future modules.

#### User Story

As a Super Administrator, I want to define roles and their permissions centrally, so that every user's access reflects a single trusted permission model.

#### Requested Capability

The system shall maintain a set of roles (Employee, HR Administrator, Manager, Super Administrator), define the permissions granted to each role across all modules, and assign roles to user accounts.

#### Functional Expectations

- Roles are defined and maintained centrally.
- Each role carries an explicit set of permissions across modules (Dashboard, Attendance, Overtime, Business Trip, Leave & Permission, User Management, Reporting).
- A user account can be assigned one or more roles.
- The effective permissions of a user reflect the union of all roles assigned to them.
- Changes to roles or role assignments are recorded for audit purposes.
- Unauthorized users cannot access permissions beyond their role set.

#### Acceptance Criteria

- The four standard roles from the project definition exist with permission sets matching the documented module permissions.
- Administrators can assign or change a user's roles.
- A user's effective permissions update to reflect role changes.
- Role and permission assignment changes are captured in the audit trail (FR-012, FR-013).
- Attempts to perform actions outside the user's permission set are denied.

#### Dependencies

- FR-001 (Authentication)
- FR-011 (Role and Permission Configuration Console)

#### Assumptions

- Role membership is assigned by authorized administrators; self-assignment is not permitted.
- Roles can overlap; combined permissions are the union of assigned roles.

#### Risks / Open Questions

- Should role assignments support department-level scoping (e.g., a Manager sees only their team)?
- Is a role hierarchy needed (e.g., inheritance between roles)?

#### Notes for Senior Software Lead Designer

Model permissions as capabilities that map to navigation items, pages, actions, and data scopes. Ensure the permission model is extensible so future modules (Payroll, Recruitment, etc.) can register their own permissions.

### - [x] FR-003: Dynamic Role-Based Navigation and Page Access Control

- Module: Core - RBAC / User Experience
- Type: Security / Functional
- Priority: Critical
- Status: Proposed
- Designed: 2026-08-06 by Senior Software Lead Designer (see `TODO.md` §1–§9)
- Requested By: Senior Software Solution Consultant
- Date: 2026-08-06
- Source Reference: Project.txt - System Architecture (Navigation dynamically controlled by RBAC), Core Functional Requirements (Permission-based navigation)
- Target Roles: All roles

#### Business Objective

Because every user opens the same application, the system must render only the menus and pages each user is permitted to see. Dynamic navigation prevents confusion, reduces unauthorized exposure, and enforces role boundaries at the presentation layer.

#### User Story

As an Employee, I want to see only the menus and pages my role allows, so that I am not exposed to functions outside my authority.

#### Requested Capability

The system shall build the visible navigation and accessible pages from the signed-in user's effective permissions, so menus and pages reflect the user's role.

#### Functional Expectations

- The main menu shows only items the user's permissions allow.
- Direct access to a page the user lacks permission for is denied.
- Users cannot see menu entries for modules they cannot use.
- Navigation reflects permission changes on the next appropriate refresh.

#### Acceptance Criteria

- An Employee sees only Employee-scope menus (Dashboard, Attendance, Overtime, Business Trip, Leave & Permission) and no User Management or Reporting menus.
- An HR Administrator sees administrative menus including User Management and Reporting.
- Entering a URL for a disallowed page is blocked and the user is returned to an allowed page.
- Super Administrator sees all configured menus.

#### Dependencies

- FR-002 (Role-Based Access Control)

#### Assumptions

- Navigation structure is centralized and driven by permissions rather than hard-coded per role.

#### Risks / Open Questions

- Should navigation ordering differ by role?
- Should partially permitted modules show reduced sub-menus?

#### Notes for Senior Software Lead Designer

Ensure page-level access control is enforced consistently whether the user navigates via menu or by direct URL entry. Navigation definitions should be data/configurable, not duplicated per role.

### - [x] FR-004: Action-Level Permission Enforcement

- Module: Core - RBAC
- Type: Security
- Priority: Critical
- Status: Proposed
- Designed: 2026-08-06 by Senior Software Lead Designer (see `TODO.md` §1–§9)
- Requested By: Senior Software Solution Consultant
- Date: 2026-08-06
- Source Reference: Project.txt - System Architecture (actions dynamically controlled by RBAC), Core Functional Requirements (Permission-based API authorization)
- Target Roles: All roles

#### Business Objective

Menus alone do not protect data; individual actions (submit, approve, reject, correct, export, deactivate) must be controlled. Action-level enforcement prevents users from performing operations their role does not allow.

#### User Story

As an HR Administrator, I want to perform only the actions my role permits, so that administrative operations cannot be misused.

#### Requested Capability

The system shall control individual actions within each page based on the user's effective permissions, showing or enabling only those actions the user may perform.

#### Functional Expectations

- Each actionable capability (e.g., Clock In, Submit Request, Approve, Reject, Correct Attendance, Export, Deactivate User) maps to a permission.
- A user only sees and can execute actions for which they hold permission.
- Attempts to execute a disallowed action are denied and logged.
- Action availability adapts to role changes.

#### Acceptance Criteria

- An Employee cannot see or invoke Approve/Reject actions on requests.
- An HR Administrator can approve or reject leave, overtime, and business trip requests.
- An Employee without User Management permission cannot create or deactivate users.
- A denied action attempt is recorded in the activity log (FR-013).

#### Dependencies

- FR-002 (Role-Based Access Control)
- FR-003 (Dynamic Navigation)

#### Assumptions

- Action permissions are granular enough to differentiate submit, review, approve, reject, correct, and export behaviors.

#### Risks / Open Questions

- Should approval authority be restricted to a user's department or reporting line (data scope) in addition to the action permission?

#### Notes for Senior Software Lead Designer

Treat actions as capabilities enforced both in the interface and at the authorization boundary, so interface hiding is never the only control.

### - [x] FR-005: Permission-Based API Authorization Enforcement

- Module: Core - RBAC / API Access
- Type: Security
- Priority: Critical
- Status: Proposed
- Designed: 2026-08-06 by Senior Software Lead Designer (see `TODO.md` §1–§9)
- Requested By: Senior Software Solution Consultant
- Date: 2026-08-06
- Source Reference: Project.txt - System Architecture (API access dynamically controlled by RBAC), Core Functional Requirements (Permission-based API authorization)
- Target Roles: All roles

#### Business Objective

Client-side hiding is not security. Every operation must be re-authorized server-side so that direct API calls cannot bypass the interface restrictions. This is essential for an enterprise-grade, auditable HRIS.

#### User Story

As a Super Administrator, I want every operation re-authorized at the access boundary, so that interface restrictions cannot be bypassed by direct requests.

#### Requested Capability

The system shall authorize every protected operation at the access boundary using the signed-in user's effective permissions, independent of what the interface displays.

#### Functional Expectations

- Every protected operation requires a valid authenticated session.
- Every protected operation checks the user's permission for that specific action.
- Denied operations return a denial response and are logged.
- The permission check cannot be bypassed by crafting direct requests.

#### Acceptance Criteria

- A user calling an operation outside their permission set receives a denial and no data is returned or changed.
- An Employee attempting a User Management operation via direct request is denied.
- Denied requests are recorded in the activity/audit log.
- All CRUD and workflow operations respect the permission matrix.

#### Dependencies

- FR-001 (Authentication)
- FR-002 (Role-Based Access Control)
- FR-004 (Action-Level Permission Enforcement)

#### Assumptions

- Authorization is enforced consistently for every operation, not only for commonly used ones.

#### Risks / Open Questions

- Should data-scope restrictions (e.g., Manager may only act on their team) also be enforced at this boundary?

#### Notes for Senior Software Lead Designer

Implement authorization as a cross-cutting control so every operation passes through the same permission check. Data scoping should be considered alongside action permissions.

### Business Objective

The role creation experience must provide an **Initial Permissions** capability.

Authorized administrators must be able to:

- Define role level.
- Define role capabilities during creation.
- Select granular permissions.
- Define data scope.
- Configure approval authority.
- Configure reporting/export access.
- Preview resulting access.
- Create roles that can immediately be assigned to users.

Role levels must support authority and visibility grouping without creating multi-level approval chains.

### User Stories

- As a Super Administrator or Role Administrator, I want to create a role with a role level and initial permissions so that assigned users immediately receive the intended access.
- As an administrator creating a user, I want to assign newly created roles without losing the current workflow.
- As a higher-level administrator, I want appropriately configured roles to access broader request data and approval/reporting functions.

### Assumptions

- Permissions are additive by default.
- Role level controls authority grouping, visibility, escalation, and reporting scope.
- Role level does not create sequential approval chains.
- Approval permission is shared across supported request types initially.
- Higher-level access must be explicitly configured.
- Existing RBAC infrastructure will be extended.
- Reports will be enhanced rather than rebuilt.
- Field-level permissions are out of scope for the initial release.

### Design Notes

> Role Level and Initial Permissions must be first-class parts of role creation.
>
> The permission checklist must support both lower-level and higher-level roles.
>
> Higher-level roles must be configurable for broad request visibility, approval, completed-request detail access, and reporting/export.
>
> Lower-level roles must be restrictable to personal or limited-scope data.
>
> The same permission model must control navigation, page access, actions, approval screens, Reports, Excel export, API authorization, and administrative capabilities.
>
> Role levels support authority and escalation scenarios only. They must never introduce multi-level sequential approval workflows.
