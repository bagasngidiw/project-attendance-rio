## Root Cause Analysis of the Current (Buggy) Implementation

Inspection of `frontend/src/features/attendance/ClockInOutPanel.tsx`, `contracts/attendance.ts`, `backend/src/presentation/dto/attendance.dto.js`, `backend/src/application/attendance.service.js`, `backend/src/domain/attendance.js`, and `backend/src/infrastructure/models/attendance.model.js`:

| # | Root cause | Evidence |
|---|-----------|----------|
| 1 | **No photo capture** — the camera only shows a live `<video>` preview; there is no capture action, no captured-photo preview, and no retake. The "captured" state is faked: `camera: { status: "captured", capturedAt }` is sent with **no actual media reference**. | `ClockInOutPanel.tsx` `submitClock()` sends `camera: { status: "captured", capturedAt }`; no canvas capture anywhere. |
| 2 | **No media upload / persistence** — the backend DTO accepts `camera.mediaRef` but the attendance service **drops** location/verification/camera entirely; the `attendance` model has no location/verification/scheduleSnapshot fields. The payload is validated then discarded. | `attendance.dto.js` `clockEventDto` has `location`/`camera`; `attendance.service.js` `clockIn`/`clockOut` only use `this.now()`; `attendance.model.js` has no such fields. |
| 3 | **Camera lifecycle incomplete** — stream cleanup only happens on React unmount via one `useEffect` cleanup; there is no capture/retake flow, no "already in use" state, no StrictMode double-mount protection (dev), no explicit "camera active" state distinct from permission. | `ClockInOutPanel.tsx` lines 69–73; states limited to idle/requesting/ready/denied/unavailable/error. |
| 4 | **Location is text-only** — no map display, no marker, no visual "Lokasi Anda"; `getCurrentPosition` is used once with a fixed 100 m "low accuracy" branch; no retry-with-timeout UX; no accuracy-threshold configuration. | `ClockInOutPanel.tsx` lines 105–131; location rendered as a `<p>` only. |
| 5 | **No device information container** — jamkerja requires a separate expandable "Info Perangkat" accordion; none exists. | No such component. |
| 6 | **Submission readiness is wrong** — `verificationReady = cameraReady && locationState === "found"` but `cameraReady` becomes true merely when the stream starts, **before any photo is captured**; so a user can submit without a photo. | `ClockInOutPanel.tsx` line 66. |
| 7 | **No route-safety guarantee** — navigation away relies on component unmount; if the shell keeps the component mounted (layout caching) or navigation happens without unmount, the camera stream persists. No explicit route-change cleanup, no location watcher cleanup (not using watch, but no guard), no timer/listener cleanup. | `ClockInOutPanel.tsx` cleanup only on unmount. |
| 8 | **Timestamp handling** — the server is authoritative (good), but `location.timestamp` is a client timestamp; the design must document storage/display/timezone (FR-009). | `ClockInOutPanel.tsx` line 117 uses `position.timestamp`. |

**The revamp must fix all of the above.** The target UX (UIUXABSENSI.md) requires: separate device-info accordion, camera container with live preview → capture → retake, location container with a real map + marker + status + retry, and a gated attendance submission action.

# FR-001: Attendance Verification Hook & State Machine (Frontend Foundation)

## 1. Objective

Create a reusable React hook + state machine that owns the complete Absensi verification lifecycle: camera (MediaStream), geolocation, device info, capture/retake, readiness, and cleanup. This is the foundation the UI components consume.

## 2. Existing Architecture Affected

- `frontend/src/features/attendance/ClockInOutPanel.tsx` (replace its inline camera/location logic).
- New file: `frontend/src/features/attendance/useAttendanceVerification.ts`.
- New file: `frontend/src/features/attendance/deviceInfo.ts` (pure detection helpers).

## 3. Camera Lifecycle (jamkerja §2 — very important)

- The camera stream MUST only be active while the Absensi module is mounted **and** the user has explicitly initiated camera verification.
- **Permission ≠ active stream.** Do not auto-start the camera on page load; start only on user action.
- Expose explicit actions: `startCamera()`, `stopCamera()`, `capture()`, `retake()`.
- **Cleanup contract** (critical):
  - On component unmount → stop all MediaStream tracks.
  - On route change away from Absensi → stop all tracks.
  - On StrictMode double-mount (dev) → the cleanup from the first mount must stop its stream before the second mount starts.
  - On `stopCamera()`/`retake()` → stop existing tracks before starting new ones; never accumulate streams.
  - On component return → resources initialized fresh; no stale stream/state.
- Guard against duplicate streams: a `streamRef` single-owner pattern; every `startCamera` call first stops any existing stream.

## 4. Geolocation Lifecycle

- One-shot `getCurrentPosition` (not continuous watch) for attendance is sufficient and safer (jamkerja §13 warns against watcher leaks). If a watcher is ever used, it MUST be stopped on unmount/navigation.
- Expose actions: `requestLocation()`, `retryLocation()`.
- Timeout handling: use a configurable timeout (e.g. 15 s) and surface "timeout" as a distinct state.
- Do NOT fake location; never hardcode coordinates.

## 5. Frontend State (Camera States — jamkerja §1/§3)

```text
CameraState =
  | "idle"                  // not requested yet
  | "requesting"            // getUserMedia in flight
  | "active"                // live stream running, no photo yet
  | "captured"              // photo captured, awaiting retake/submit
  | "denied"                // NotAllowedError / PermissionDeniedError
  | "unavailable"           // NotFoundError / OverconstrainedError / no mediaDevices
  | "in_use"                // NotReadableError (camera busy elsewhere)
  | "error"                 // other failure
```

```text
LocationState =
  | "idle"
  | "requesting"
  | "found"                 // accuracy <= configured threshold (or no threshold)
  | "low_accuracy"          // accuracy > threshold, still usable if policy allows
  | "denied"
  | "unavailable"
  | "timeout"
  | "error"
```

```text
VerificationState = {
  camera: CameraState,
  photo: { dataUrl: string|null, mediaRef: string|null, capturedAt: string|null },
  location: GeoLocation | null,
  device: DeviceInfo,
  readiness: { cameraReady, photoCaptured, locationReady, complete }
}
```

## 6. Device Information (jamkerja §7)

- Detect and expose (operational only; no fingerprinting, no sensitive data):
  - Device category: `mobile | tablet | desktop` (user-agent heuristics).
  - Browser name/version.
  - Operating system.
  - Camera availability: `navigator.mediaDevices?.enumerateDevices()` filtered for `videoinput`.
  - Location availability: `navigator.geolocation` presence.
  - Camera permission state: from `navigator.permissions.query({ name: "camera" })` where supported.
  - Location permission state: from `navigator.permissions.query({ name: "geolocation" })` where supported.
- Never attempt fingerprinting.

## 7. UI/UX

- The hook returns state + actions; the UI (FR-002/FR-003/FR-004) renders it.

## 8. Validation

- No business validation here; states are derived from browser API outcomes.

## 9. Error Handling

- Map DOMException names to states (NotAllowedError/PermissionDeniedError → denied; NotFoundError/OverconstrainedError → unavailable; NotReadableError → in_use; else → error).

## 10. Loading States

- `requesting` for both camera and location.

## 11. Permission States (jamkerja §14)

- Granted / Denied / Prompt / Unavailable for both camera and location; map from API outcomes + permission query results.

## 12. Responsive Behavior

- n/a (hook).

## 13. Testing

- Unit: state transitions (start→active→captured→retake→active); cleanup stops tracks; StrictMode double-mount safety.
- Integration: mocked `getUserMedia`/`geolocation`/`permissions`.

## 14. Acceptance Criteria

- [ ] Camera stream only active while in Absensi + explicitly started.
- [ ] Cleanup on unmount/route change stops all tracks.
- [ ] No duplicate streams.
- [ ] Location one-shot with timeout + retry.
- [ ] Device info detected without fingerprinting.

## 15. Regression Considerations

- Existing attendance page still renders; no other module touches the hook.

# FR-006: Attendance Submission (API Integration + Backend Persistence)

## 1. Objective

Wire the verification payload (photo + location + device metadata) into the existing clock-in/clock-out API, persist it on the existing attendance record, and keep the **server timestamp authoritative** (jamkerja §10, §11, §18).

## 2. Existing Architecture Affected

- `frontend/src/lib/axios.ts` (`attendanceApi.clockIn/clockOut`) — extend body.
- `backend/src/presentation/dto/attendance.dto.js` — extend `clockEventDto` (camera with mediaRef, location, device info).
- `backend/src/presentation/controllers/attendance.controller.js` — pass the payload through.
- `backend/src/application/attendance.service.js` — persist location/verification/device metadata.
- `backend/src/infrastructure/models/attendance.model.js` — add fields (FR-008).
- `backend/src/infrastructure/repositories/attendance.repository.js` — accept + store new fields.

## 3. API Contract

```text
POST /api/v1/attendance/clock-in
body: {
  camera: { status: "captured", capturedAt, mediaRef },   // mediaRef = uploaded selfie reference
  location: { latitude, longitude, accuracy, timestamp, permissionState, acquisitionStatus },
  device: { category, browser, os, cameraAvailable, locationAvailable }   // optional metadata
}
POST /api/v1/attendance/clock-out   // same shape
```

- Authentication: required (existing `attendance:clock_in`/`clock_out`).
- **Server-authoritative timestamp:** backend sets `clockInAt`/`clockOutAt` from `this.now()` (UTC). The client `location.timestamp` is stored as a separate field, never used as the official time.

## 4. Backend Validation

- Authenticated user from session (`req.auth.userId`) — never trust a client userId.
- `location` required when policy `attendance.requireLocation` true (default true); latitude/longitude range-validated; accuracy ≥ 0.
- `camera.mediaRef` required when policy `attendance.requireCamera` true (default true).
- Existing work-period rules retained (duplicate clock-in blocked; clock-out without open period blocked).

## 5. Mongo/Mongoose

- `attendance.model.js` adds:
  ```text
  clockInLocation / clockOutLocation: { latitude, longitude, accuracy, timestamp, permissionState, acquisitionStatus } (nullable)
  verification: { camera: { status, capturedAt, mediaRef }, location: { status, acquiredAt } }
  deviceInfo: Mixed (nullable, operational metadata)
  scheduleSnapshot: { workingDays[], workingStartTime, workingEndTime, evaluatedAt }   // FR-007
  ```
- No new collections for attendance; media stored by reference (FR-008).

## 6. Business Logic

- Persist the verification payload on the record; recompute status/punctuality from server timestamp + schedule snapshot (FR-007).
- Do NOT create a second attendance entity.

## 7. Error Handling

- 400 missing verification; 409 duplicate/state; 403 unauthorized; 500 generic. User-readable messages.

## 8. Testing

- Photo sent correctly; location sent correctly; backend validates authenticated user; server timestamp authoritative; clock-in/out persisted; duplicate blocked; existing history still works.

## 9. Acceptance Criteria

- [ ] Verification payload persisted on the attendance record.
- [ ] Server timestamp authoritative.
- [ ] Existing attendance history works.

## 10. Regression Considerations

- Existing history list, HR overview, and corrections must continue working after the model change (additive fields).

# FR-009: Route Safety, Cleanup & Timestamp/Timezone Integrity

## 1. Objective

Guarantee that leaving Absensi stops camera + location + timers/listeners, resources are released, returning re-initializes safely; and document server-authoritative timestamp/timezone handling (jamkerja §13, §18; penambahan §Server-Authoritative).

## 2. Existing Architecture Affected

- `frontend/src/features/attendance/useAttendanceVerification.ts` (cleanup contract, FR-001).
- `frontend/src/App.tsx` / `routes/AppRouter.tsx` — if needed, a route-level unmount guarantee (the Absensi route already unmounts its page on navigation; verify no layout keeps it mounted).

## 3. Cleanup Contract (RESOLVED)

- On unmount: stop MediaStream tracks; stop location watcher if any; clear timers; remove event listeners; revoke object URLs.
- On route change away from Absensi: the component unmount triggers the same cleanup; the Developer must verify there is no code path where the Absensi page stays mounted during navigation.
- On StrictMode double-mount: first cleanup stops the stream before second mount starts (guard via a `started` flag / `streamRef` single-owner).
- On return: initialize fresh; never reuse a stale stream/state.
- Avoid: memory leaks, duplicated streams/watchers, multiple active MediaStreams, stale references/state, camera running after navigation.

## 4. Server-Authoritative Timestamp / Timezone (RESOLVED)

- Storage format: UTC `Date` instants on `clockInAt`/`clockOutAt`.
- Organization timezone: company offset/timezone (existing `companyTimezoneOffsetMs` config; `toWorkDay`).
- Display timezone: UI renders in the company timezone (existing `toLocaleTimeString` with explicit timezone or the configured offset).
- Server timestamp: `this.now()` in `attendance.service.js` (injectable clock).
- Client timestamp handling: `location.timestamp` stored separately for reference; never used as the official attendance time.
- Timezone conversion: UTC storage; date key derived in company timezone; display converted to company timezone.
- DST: document that the company timezone offset is used; if the org timezone observes DST, the offset is evaluated at each event.
- Prevention of timestamp manipulation: server timestamp authoritative; client cannot set `clockInAt`/`clockOutAt`; corrections remain HR-only and audited.

## 5. Testing

- Navigation to Dashboard/Cuti/Sakit/Ijin/Lembur/other stops camera; no background camera access; return re-initializes safely.
- Timestamp integrity: client cannot forge the official time.

## 6. Acceptance Criteria

- [ ] No camera runs outside Absensi.
- [ ] Cleanup complete on all navigation paths.
- [ ] Server timestamp authoritative; timezone documented.

## 7. Regression Considerations

- Existing attendance history/overview/corrections unaffected by cleanup changes.
